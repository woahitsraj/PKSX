# Pokemon Storage catalog

The Pokemon Storage service owns queries and local mutations for app-owned Pokemon records, Pokemon Origin, physical placements, Storage Boxes, revisions, and deletion tombstones. Consumers use the service, not TinyBase or the persistence adapters directly. The existing version 1 nested Pokemon Storage snapshot remains readable for the separate migration issue. The catalog contains trainer and origin metadata. Future Cloud Sync is provider-readable, with no application-layer encryption; credentials and device-local state do not belong in the catalog.

`POKEMON_STORAGE_CATALOG_VERSION` versions this catalog. It is independent of `WORKSPACE_SCHEMA_VERSION`, the active Save File Workspace schema, and of the PKHeX preservation payload version. Catalog version 1 persists a structured manifest with one Storage root ID, root timestamps and Box order, stable engine Record IDs, Storage Box IDs, immutable origins, blob references, and tombstones. Reordering changes the root revision and timestamp without changing Box metadata. TinyBase holds the reactive structured projection after removing any engine-supplied entity byte field. Preservation payload bytes stay in immutable SHA-256-addressed blobs outside TinyBase. A blob reference records its digest, byte length, format, and payload schema version.

The service asks the PKHeX Engine to create, fork, and read preservation payloads. A fork gives an independent copy a new Record ID while preserving its original and current entity snapshots. TypeScript stores and checks the returned bytes but never builds Pokemon Entity bytes from a projection. Each local mutation stages and verifies required blobs, then conditionally commits one manifest revision. The browser adapter uses an IndexedDB transaction for the manifest compare and write. The native adapter writes revisioned manifests and reads the last complete generation. Its sweep shares the commit queue and retains blobs referenced by any complete committed generation. A failed commit leaves the previous complete manifest available; a staged blob without a committed reference can be swept.

At least one Storage Box must remain, and a box can be deleted only when empty. Placement collisions and references to deleted boxes are retained in the manifest for future synchronization. The service derives a deterministic visible slot by Record ID, using the next empty slot with wraparound; records without a free slot appear in derived overflow. Local additions and copies count unfiled records toward capacity and stop when capacity is full or overflow exists. Local placements cannot target raw or resolved occupied slots. The derivation never rewrites a record's persisted placement. Deletion tombstones require a Save File ID only for moves to a Save File.
