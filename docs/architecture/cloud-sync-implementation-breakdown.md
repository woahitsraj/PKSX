# Personal Cloud Sync implementation breakdown

For [Define personal Cloud Sync implementation breakdown](https://github.com/woahitsraj/PKSX/issues/473) and [Wayfinder: Cloud Sync for Saves](https://github.com/woahitsraj/PKSX/issues/302). This is an implementation plan, not permission to implement runtime code, deploy, purchase services, or change accounts.

## Decision baseline

Use the accepted provider-neutral [adapter contract](cloud-sync-provider-adapter-contract.md), [intervention workflow](cloud-sync-intervention-workflow.md), CONTEXT.md, and ADRs 0004, 0018, and 0020. The following user-approved specifications are in focused PRs and must land before dependent implementation:

- [Select Cloudflare and Better Auth for Cloud Sync](https://github.com/woahitsraj/PKSX/pull/465): Workers, SQLite-backed Durable Objects, private R2, Better Auth, and D1; PKSX operates identity and email integration.
- [Define Cloud Sync account settings and space management](https://github.com/woahitsraj/PKSX/pull/469): one settings Takeover, account controls, usage attribution, and existing domain deletion actions.
- [Specify personal Cloud Sync access and initial quota](https://github.com/woahitsraj/PKSX/pull/470): only the maintainer's account, hidden UI and service authorization, maintainer funding, initial configurable 1 GiB content quota. Budget and future public billing remain open.
- [Define passkey-first Cloud Sync sign-in and linking](https://github.com/woahitsraj/PKSX/pull/471): first account setup through Google/Apple, immediate passkey enrollment offer, passkey-first return sign-in, explicit linking across different provider emails, one primary verified email and one Sync Profile, codes last.

Treat public subscriptions as a separate future product. The personal release has no checkout, billing integration, public registration, upgrade prompts, additional social providers, Peer Transfer, or Electron packaging.

## Existing ownership boundaries

Raw Save File, Workspace, and Backup persistence lives under `src/lib/pksx/saves/`; Workspace editing persistence also uses `src/lib/pksx/workspace-store/`. Pokemon Storage persistence lives under `src/lib/pksx/pokemon-storage-catalog/`, with mutations integrated through `src/lib/pksx/storage-operations/` and `src/lib/pksx/storage-workbench/`. These are existing boundaries to inspect before implementation, not claims that those modules already implement Cloud Sync.

Put revision validation, causal decisions, queue scheduling, and migrations in provider-neutral code with explicit inputs and durable storage ports. The provider adapter transports opaque records and raw artifacts and enforces authorization, transport completeness, and conditional storage operations. It never picks a conflict winner or migrates payload schemas. The PKHeX Engine remains the only Pokemon-byte authority; transporting preservation artifacts requires no TypeScript serializer or new engine implementation.

The UI consumes domain outcomes and actionability. Do not scatter provider SDK calls through Saves mutations or surface automatic transient failures as notifications. Only the service adapter knows Cloudflare-specific identifiers, and credentials/enrollment/UI state stay installation-local.

## Verification order

Start with deterministic coordinator and persistence tests using a credential-free fake adapter and a controllable clock. Prefer a few behavioral scenarios that cross restart boundaries over tests mirroring every method. Reuse those observable contract scenarios against the provider adapter in an isolated environment when such integration is authorized.

Before UI integration, demonstrate crash recovery after artifact completion and after publication commit, coherent Save/Storage acceptance, a cleanup/recovery race, and cross-profile denial. Before native handoff, demonstrate real system-browser return and cold-start behavior plus secure credential access. No correctness requirement may depend on a suspended app executing background JavaScript.

Implementation PRs run the repository's applicable lint, typecheck, unit, engine-smoke, and e2e checks. Engine changes additionally require dotnet build and format verification; this plan does not anticipate engine changes. Verify against each issue's acceptance on its actual branch, preserve required evidence outside the repository, and report every incomplete integration check honestly. No code tests are claimed to have passed by this document.

## Deployment gates and unresolved choices

The maintainer must settle the total operating budget before a hosted environment is provisioned. Prepare an email-delivery and hosting-plan recommendation with actual limits; no vendor, plan purchase, or amount is selected by this breakdown. Obtain credentials only through the authorized secret-handling flow when they become necessary, not in issue bodies or chat.

Owner provisioning needs a verified stable account identity and a private activation path, not an email string trusted from the client. Google/Apple credentials, passkey RP origin, native associated links, delivery configuration, monitoring, and a durable account-erasure runbook are deployment prerequisites. Budget and credentials must not block the independent credential-free coordinator units, but must block production rollout.

Public paid availability, pricing, subscriptions, payment handling, and post-subscription data access are undecided and outside the personal implementation. They do not need to be designed before the personal coordinator, but require their own explicit product decisions before any public release.

This plan can be split into implementation issues after its documentation dependencies land and runtime work is authorized. Do not label deployment or public billing ready, close the Cloud Sync map, or infer runtime authorization from a planning PR.
