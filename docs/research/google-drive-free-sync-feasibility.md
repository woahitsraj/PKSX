# Google Drive as a free Cloud Sync option

Research for [Assess Google Drive as a free Cloud Sync option](https://github.com/woahitsraj/PKSX/issues/479), requested after the initial Cloudflare provider decision. This assesses an additional user-funded-storage option; it does not select a new provider, alter the personal access gate, or authorize implementation, account changes, or purchases.

## Recommendation

Google Drive is a credible candidate for an optional free-to-the-user PKSX sync mode that stores artifacts in the user's own Drive. It could remove PKSX's hosted artifact-storage bill for those users. It is not a drop-in implementation of the accepted Cloud Sync contract, and no evidence here establishes zero operating cost or safe concurrent sync.

Investigate it as an alternative provider behind the same provider-neutral coordinator. Preserve immutable revisions, conflict recoveries, and coherent changes in the free option. Do not make safe conflict handling a paid benefit or implement a shared mutable archive whose last upload silently wins. Keep the selected Cloudflare personal rollout while evaluating this candidate; public availability and free/paid packaging require a separate decision.

## What the reference actually does

Inspected pokemon-fulldex at commit `4607874538eda24cb24730a2b4d8900312a72592`. Its Drive adapter uses the scoped `drive.file` permission and a visible application folder, with one mutable file per save and metadata in appProperties. It compares local and remote hashes against a last-synchronized hash, exposes conflicts, and backs up bytes before replacement. Automatic upload waits for a quiet period after a local save. [Drive adapter and reconciliation](https://github.com/mamesj/pokemon-fulldex/blob/4607874538eda24cb24730a2b4d8900312a72592/frontend/cloud_saves.cpp#L383), [automatic sync](https://github.com/mamesj/pokemon-fulldex/blob/4607874538eda24cb24730a2b4d8900312a72592/frontend/cloud_autosync.cpp)

Its Drive write is a create or unconditional PATCH after checking remote state, not PKSX's immutable publication protocol. **Inference:** the inspected path does not establish preservation of two simultaneous writers that both observed the same baseline. Its per-save model also does not demonstrate coherent Workspace/Pokemon Storage changes, permanent deletion markers, or cross-device Conflict Recoveries. These are differences in requirements, not a claim that the reference lacks useful safeguards. No reference tests were executed.

## Cost and authorization

Google describes standard Drive API use as available at no additional cost, subject to quotas. The current limits page also announces future charges for excess quota usage and documents daily request/egress thresholds. **Inference:** a free product tier is plausible, but it must not promise unlimited API capacity or perpetual zero developer cost. User storage, Google account limits, support, consent configuration, and maintenance still matter. No budget estimate is measured here. [Drive limits and pricing](https://developers.google.com/workspace/drive/api/guides/limits)

Request narrow scopes, not access to all Drive files. Google lists `drive.file` for app-created or user-selected files and `drive.appdata` for hidden app data as non-sensitive scopes. The latter hides ordinary files from the user's Drive UI, but the user can still delete the app data through Drive management; it cannot be treated as permanent recovery outside the user's control. Unlike ordinary Drive files, app-data files cannot be moved to trash. A scope choice is still open; the reference's choice is evidence, not a PKSX decision. [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [app data behavior](https://developers.google.com/workspace/drive/api/guides/appdata)

Drive exposes account storage usage and limits through `about.storageQuota`, and file byte usage through `quotaBytesUsed`. **Inference:** show the user's available Drive capacity separately from PKSX content usage; the account is shared with other services, so available capacity can change independently of PKSX. This is not the same quota policy as the selected managed provider's configurable 1 GiB allowance. [Account quota](https://developers.google.com/workspace/drive/api/reference/rest/v3/about), [file quota bytes](https://developers.google.com/workspace/drive/api/reference/rest/v3/files)

A passkey or Apple sign-in does not grant Drive access. A Drive mode needs separate Google consent, and an Apple-only user would still need a Google account for storage. The reference's limited-input device authorization is not a required interaction for PKSX web/mobile: use an appropriate Google web/native authorization flow, rather than copying a TV/Switch code-entry flow. Credentials must not be copied from the C++ reference into a browser bundle or ordinary settings file. [Google authorization](https://developers.google.com/identity/protocols/oauth2), [native apps](https://developers.google.com/identity/protocols/oauth2/native-app), [limited-input devices](https://developers.google.com/identity/protocols/oauth2/limited-input-device)

Google's external OAuth Testing status normally gives Drive-authorized refresh tokens a seven-day lifetime. A browser-only token flow also does not provide the same refresh-token custody as a server or installed app. **Inference:** verify returning-user renewal on web and native before promising unobtrusive sync; avoiding a storage backend does not automatically avoid all backend or reauthorization needs. [Token lifetime rules](https://developers.google.com/identity/protocols/oauth2#expiration), [offline access by application type](https://developers.google.com/identity/protocols/oauth2/web-server#offline)

## Fit with the accepted adapter contract

- **Immutable upload and retry:** Drive supports resumable uploads and pre-generated file IDs; retrying creation at the same ID avoids duplicate creation. Use PKSX revision identities separately from provider file IDs and verify complete bytes after uncertain results. A filename search is not an idempotency key. [Resumable uploads and retry](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [pre-generated ID spaces](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/generateIds)
- **Coherent publication:** upload immutable artifacts and revision records, then an immutable descriptor naming the complete coherent change. **Inference:** the existing coordinator can stage incomplete descriptor arrivals, but this needs proof on Drive; no multi-file transaction is established by the sources reviewed here. Keep concurrent heads rather than replacing a single latest-save file.
- **Catch-up:** Drive has paginated change retrieval and start tokens. A durable enumeration/reconciliation strategy still needs proof, including interrupted initial discovery and account reconnection. Push notification channels require a reachable HTTPS endpoint and renewal, so a backend-free browser option should investigate foreground/resume catch-up rather than claiming native WebSocket-style delivery. Foreground sync can still be automatic. [Changes](https://developers.google.com/workspace/drive/api/guides/manage-changes), [push channels](https://developers.google.com/workspace/drive/api/guides/push)
- **Recovery retention:** ordinary Drive revision history is not PKSX's Conflict Recovery store. Older binary revisions can be purged, and only 200 per file can be marked keepForever. Store durable PKSX recovery states as explicit objects under PKSX rules. [Drive revision retention](https://developers.google.com/workspace/drive/api/guides/manage-revisions)
- **Conditional cleanup:** the reviewed sources do not establish the accepted atomic guard between deleting content and a concurrent new recovery reference. A safe design must prove that race or retain content until it can do so; silently dropping the guard is not an adapter implementation. More restrictive garbage collection increases storage use and therefore is also a product trade-off.
- **Quota-full deletion:** Drive storage exhaustion must not silently lose pending changes or make local editing unusable. Prove how deletion markers and ancestry remain writable when Drive is full. A provider that cannot reserve or otherwise guarantee that metadata capacity needs an explicit contract decision, not a hidden downgrade.
- **Revocation and account deletion:** logging out of PKSX, disconnecting Drive, deleting a PKSX account, and deleting Google-owned data are distinct actions. If access has already been revoked, PKSX cannot claim it erased inaccessible Drive files. Direct Google grants also need their own revocation policy across installations. [OAuth revocation](https://developers.google.com/identity/protocols/oauth2/javascript-implicit-flow#tokenrevoke)

## Decisions a free Drive mode would reopen

The current specification has one provider owning identity and storage, one personal Sync Profile per User Account, managed quota and erasure semantics, passkey/Google/Apple access through the selected identity service, and a hidden maintainer-only initial release. Combining PKSX Better Auth identity with Google-owned storage qualifies the single-provider boundary. A standalone Google-backed mode would instead need to explain its own profile ownership and how passkeys or Apple relate to it. Neither option is approved by this feasibility study.

Mode changes also need explicit transfer/adoption rules. Do not synchronize the same active Sync Profile concurrently through Cloudflare and Drive without a separate coordination design, and do not duplicate or silently upload Saves when connecting another Google account. A free public option does not implicitly remove the personal rollout gate from the existing provider.

## Next evidence and product decision

The strongest next technical study is a small separately authorized adapter spike: two concurrent writers, a dropped commit response, a descriptor arriving before dependencies, recovery creation racing cleanup, a full Drive account, revoked authorization before deletion, and web/native renewal. No real Google account, provider test, runtime prototype, or local suite was used here.

Recommendation for discussion: retain the managed personal provider as selected and evaluate a second, optional Google Drive mode whose user-facing difference is storage/account ownership, not weaker preservation guarantees. A simpler explicit Drive backup/restore feature is also feasible to investigate, but must be named and scoped separately rather than presented as full Cloud Sync. The free/paid product split remains a recommendation until the user decides.

Verification was limited to primary documentation, pinned source inspection, and a focused sequential Markdown check. The Mac's full-suite verification window is reserved for the Switch trade track; this investigation starts no Vitest, Playwright, lint/typecheck, or dotnet suite and claims none passed.
