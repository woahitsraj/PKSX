# Web and Capacitor Cloud Sync constraints

Research for [Research web and Capacitor sync and secure-storage constraints](https://github.com/woahitsraj/PKSX/issues/308), a ticket on the map [Wayfinder: Cloud Sync for Saves](https://github.com/woahitsraj/PKSX/issues/302).

**Question.** What reliable background-execution, network-retry, persistent-storage, cryptography, and secure-key-storage capabilities constrain a shared Cloud Sync lifecycle and provider-neutral privacy design on web/PWA and Capacitor?

**Sources.** Web platform specifications and MDN, Capacitor 8 documentation, Apple Developer Documentation, and Android Developers documentation. PKSX currently uses Capacitor 8.4.x, so the Capacitor findings use the matching v8 documentation. [PKSX package manifest](../../package.json)

## Answer

The portable Cloud Sync contract must be **foreground-first, durable, restartable, and idempotent**. It may request background work, but it cannot promise when, how often, or even whether a background run happens. Every run must reload durable state, process a bounded unit, checkpoint atomically, and tolerate termination and duplicate delivery. This follows from service workers being time-limited and restartable, the web background-sync APIs not being available across PKSX's browser baseline, and Capacitor's cross-platform background window being approximately 30 seconds with non-guaranteed scheduling. [Service Workers specification](https://www.w3.org/TR/service-workers/#service-worker-concept), [MDN Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API), [Capacitor Background Runner](https://capacitorjs.com/docs/apis/background-runner#limitations-of-background-tasks)

The provider-neutral design also needs a **platform key-custody boundary**, separate from the sync protocol and ciphertext format. Web Crypto can create non-extractable keys, but the standard does not guarantee hardware-backed or encrypted-at-rest key storage. Capacitor can reach iOS Keychain and Android Keystore through native code, but Capacitor's Preferences and Filesystem plugins are not secure-key stores. [Web Cryptography Level 2, key storage and security considerations](https://www.w3.org/TR/WebCryptoAPI/#concepts-key-storage), [Apple Keychain Services](https://developer.apple.com/documentation/security/keychain-services), [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [Capacitor custom native plugins](https://capacitorjs.com/docs/plugins/creating-plugins)

## Web/PWA limits

### Background work

A service worker is an event-driven context that the browser may terminate when idle and restart for a later event. Its global state is not preserved. `event.waitUntil()` extends an event's lifetime, but a browser can still stop work that exceeds its time limit, and an interrupted handler restarts from the beginning rather than resuming. [Service Workers specification](https://www.w3.org/TR/service-workers/#service-worker-concept), [MDN `ServiceWorkerGlobalScope`](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope), [MDN offline and background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

One-shot Background Sync can wake a service worker after connectivity returns, but it is not Baseline because major browsers do not all implement it. Registration happens while the app is open, retries are limited, and run duration is browser-limited. Periodic Background Sync is also non-Baseline and experimental; the requested interval is only a minimum, and delivery can depend on permission, installation, engagement, and browser policy. Neither API can be part of PKSX's cross-browser correctness contract. [MDN Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API), [MDN Periodic Background Synchronization API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Periodic_Background_Synchronization_API), [MDN offline and background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

`navigator.onLine` can report a LAN connection with no Internet reachability, and its behavior varies by operating system and browser. PKSX should therefore attempt the provider request and classify its result; online/offline events may prompt a retry but must not decide whether syncing is possible. [MDN `navigator.onLine`](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine)

### Durable state

IndexedDB is available to service workers, is transactional, and can store structured data and blobs. It is suitable for the outbox, remote-observation state, resumable-transfer checkpoints, and encrypted artifact bytes, but the application must implement synchronization semantics itself. [MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API), [MDN IndexedDB terminology](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Basic_Terminology)

Browser origin storage is best-effort by default. `navigator.storage.persist()` requests durable storage, but the browser may deny the request; users can still explicitly clear persistent data. PKSX can request persistence after Cloud Sync is enabled and must surface a degraded durability state when it is not granted. [MDN storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [MDN `StorageManager.persist()`](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/persist)

### Web key custody

Web Crypto keys can be marked non-extractable, restricted to specified operations, serialized, and stored in IndexedDB. Non-extractable means `exportKey()` and `wrapKey()` fail; it does not prevent same-origin code from invoking permitted operations with the key. [Web Cryptography Level 2, `CryptoKey`](https://www.w3.org/TR/WebCryptoAPI/#cryptokey-interface), [MDN `CryptoKey.extractable`](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey/extractable), [MDN SubtleCrypto](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto)

The Web Crypto specification provides no key store and makes no normative guarantee that underlying key material is hardware-backed, encrypted on disk, or inaccessible to another process with the browser's privileges. It also warns that script injection is equivalent to remote code execution and that cleared origin storage can destroy persisted keys. Consequently, a web-only non-extractable key is useful hardening, not a device-grade secure-storage guarantee or a recovery plan. [Web Cryptography Level 2, key storage](https://www.w3.org/TR/WebCryptoAPI/#concepts-key-storage), [Web Cryptography Level 2, security considerations](https://www.w3.org/TR/WebCryptoAPI/#security-developers)

## Capacitor limits

### Background execution and transport

Capacitor's WebView is unavailable during native background events. Background Runner instead loads a standalone, headless JavaScript context. That context has no DOM, keeps no state between invocations, exposes a limited API set, and documents only a simple UserDefaults/SharedPreferences-backed string store for persistence. The documented `fetch` subset does not support a `Request` object. A shared sync engine can reuse pure protocol code in this context, but access to PKSX's application database, files, and native keys requires explicit native/plugin bridges. [Capacitor Background Runner overview](https://capacitorjs.com/docs/apis/background-runner#about-background-runner), [JavaScript API](https://capacitorjs.com/docs/apis/background-runner#javascript-api), [runner lifetimes](https://capacitorjs.com/docs/apis/background-runner#runner-lifetimes), [CapacitorKV](https://capacitorjs.com/docs/apis/background-runner#capacitorkv)

On iOS, each Background Runner invocation has approximately 30 seconds, requested intervals are not guaranteed, the operating system chooses actual execution based partly on app use, and background tasks do not run in the simulator. On Android, a runner may have up to 10 minutes, but Capacitor recommends a 30-second cross-platform bound; repeating tasks have a minimum 15-minute interval and actual timing is subject to battery policy. [Capacitor Background Runner limits](https://capacitorjs.com/docs/apis/background-runner#limitations-of-background-tasks)

Apple's native `BGAppRefreshTask` similarly receives at most 30 seconds and is launched when the system decides. `BGProcessingTask` can run for minutes but may be interrupted. For file uploads and downloads, a background `URLSession` transfers in a separate process and can continue across suspension or system termination, but a user force-quit cancels transfers until the user relaunches the app. [Apple choosing background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app), [Apple `BGProcessingTask`](https://developer.apple.com/documentation/backgroundtasks/bgprocessingtask), [Apple background URLSession](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:))

Android WorkManager is the recommended persistent scheduler for work that must survive leaving the screen, app exit, and device reboot. It supports network and battery constraints plus linear or exponential retry backoff. Execution timing is still inexact, ordinary background work is time-limited, and periodic work has a 15-minute minimum. [Android WorkManager overview](https://developer.android.com/develop/background-work/background-tasks/persistent), [Android work requests and retry](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [Android `PeriodicWorkRequest`](https://developer.android.com/reference/androidx/work/PeriodicWorkRequest)

These limits require sync units smaller than one invocation, with durable cursors and idempotent remote operations. A native transport adapter may use background `URLSession` or WorkManager, while the shared lifecycle remains correct if only foreground runs ever occur. This is an inference from the documented executor limits and restart behavior. [Capacitor Background Runner limits](https://capacitorjs.com/docs/apis/background-runner#limitations-of-background-tasks), [Apple background URLSession](https://developer.apple.com/documentation/foundation/urlsessionconfiguration/background(withidentifier:)), [Android WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent)

### Persistent storage and backup

Capacitor Preferences is a lightweight string key/value store backed by UserDefaults on iOS and SharedPreferences on Android. It is not intended as a database, and its PWA implementation falls back to `localStorage`. It is appropriate for small configuration, not artifact bytes or a transactional sync queue. Android also explicitly advises against storing credentials and authentication tokens in SharedPreferences or files. [Capacitor Preferences](https://capacitorjs.com/docs/apis/preferences), [Android Auto Backup](https://developer.android.com/identity/data/autobackup)

Capacitor Filesystem provides app file storage. `Data` maps to Documents on iOS and app files on Android; `Library` maps to application files on both; both are removed on Android uninstall. `LibraryNoCloud` explicitly prevents iOS cloud backup. Android Auto Backup otherwise includes most internal files, databases, and SharedPreferences by default, with a 25 MB per-app limit, unless backup rules exclude them. PKSX must explicitly choose which local replicas and queue state may be restored, and must exclude device-bound keys, credentials, leases, and stale in-flight state. [Capacitor Filesystem `Directory`](https://capacitorjs.com/docs/apis/filesystem#directory), [Android Auto Backup](https://developer.android.com/identity/data/autobackup)

### Native key custody and background access

Apple Keychain is the native store for small secrets and cryptographic keys. The default `WhenUnlocked` accessibility makes an item unavailable while the device is locked. `AfterFirstUnlock` permits background access after the first unlock following reboot; its `ThisDeviceOnly` form prevents migration to another device. File protection has the same tradeoff: `complete` blocks access while locked, while `completeUntilFirstUserAuthentication` remains accessible after the first unlock. [Apple Keychain Services](https://developer.apple.com/documentation/security/keychain-services), [restricting keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility), [`AfterFirstUnlockThisDeviceOnly`](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly), [Apple file protection](https://developer.apple.com/documentation/foundation/fileprotectiontype)

Android Keystore keeps key material non-exportable, can bind it to secure hardware when available, and can restrict operations by purpose or user authentication. A key configured to require authentication or an unlocked device can fail in unattended background work, and authentication-bound keys can be invalidated by lock-screen or biometric changes depending on configuration. Hardware backing is optional and must be queried. [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [`setUserAuthenticationRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean)), [`setUnlockedDeviceRequired`](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUnlockedDeviceRequired(boolean))

Capacitor 8's documented Preferences and Filesystem APIs expose key/value and file operations, not Keychain or Keystore operations. PKSX therefore needs a native key-custody plugin or equivalent native implementation. Its interface must make background availability, device-only status, loss/invalidation, and deletion explicit rather than exposing a generic string store. This is an inference from the official plugin APIs and native secure-store requirements. [Capacitor Preferences](https://capacitorjs.com/docs/apis/preferences), [Capacitor Filesystem](https://capacitorjs.com/docs/apis/filesystem), [Capacitor plugin API](https://capacitorjs.com/docs/plugins/creating-plugins), [Apple Keychain Services](https://developer.apple.com/documentation/security/keychain-services), [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

## Requirements this evidence fixes

1. **Correctness cannot depend on background execution.** Foreground launch/resume and explicit Retry are mandatory triggers; background sync is an enhancement. [MDN Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API), [Capacitor Background Runner limits](https://capacitorjs.com/docs/apis/background-runner#limitations-of-background-tasks)
2. **The queue is the source of truth.** Persist intent, attempt count, next-attempt time, idempotency identity, transfer cursor, and last terminal error before scheduling work. This follows from executor state being discarded or processes being stopped and restarted. [Service Workers specification](https://www.w3.org/TR/service-workers/#service-worker-concept), [Capacitor runner lifetimes](https://capacitorjs.com/docs/apis/background-runner#runner-lifetimes)
3. **Runs are bounded and resumable.** The portable budget is about 30 seconds. Commit a checkpoint after each artifact or chunk and assume the executor can disappear immediately afterward. [Capacitor Background Runner limits](https://capacitorjs.com/docs/apis/background-runner#limitations-of-background-tasks), [MDN offline and background operation](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)
4. **Connectivity signals only prompt attempts.** Success, retryability, authentication failure, conflict, and quota failure come from provider responses, not `onLine` or plugin network status. [MDN `navigator.onLine`](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/onLine)
5. **Storage durability is observable.** Request persistent web storage, report when it is denied, track quota, and define native backup exclusions and restore reconciliation. [MDN storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Android Auto Backup](https://developer.android.com/identity/data/autobackup), [Capacitor Filesystem](https://capacitorjs.com/docs/apis/filesystem#directory)
6. **Protocol and key custody are separate adapters.** The provider adapter handles remote manifests and ciphertext. The key-custody adapter handles non-extractable web keys or native Keychain/Keystore keys and reports whether unattended background use is allowed. This is an architectural inference from the platforms exposing different key guarantees. [Web Crypto security considerations](https://www.w3.org/TR/WebCryptoAPI/#security-developers), [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services), [Android Keystore](https://developer.android.com/privacy-and-security/keystore)
7. **Background access is a privacy choice.** Keys that require user presence give stronger local protection but preclude unattended sync; background-accessible keys weaken that gate. The PRD must choose and explain the tradeoff. [Apple keychain accessibility](https://developer.apple.com/documentation/security/restricting-keychain-item-accessibility), [Android authentication-bound keys](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))
8. **Key loss and device replacement need a product decision.** Web storage clearing, app uninstall, device-only native keys, and native key invalidation can all remove access to local keys. Cross-device encrypted sync therefore needs an explicit enrollment and recovery mechanism, not an implicit promise that device storage survives. [Web Crypto security considerations](https://www.w3.org/TR/WebCryptoAPI/#security-developers), [Capacitor Preferences](https://capacitorjs.com/docs/apis/preferences), [Apple `AfterFirstUnlockThisDeviceOnly`](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly), [Android authentication-bound keys](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder#setUserAuthenticationRequired(boolean))

## Newly sharpened decisions

The evidence makes three previously broad areas precise enough for decision tickets:

- What foreground triggers, durable queue states, retry classes, backoff bounds, and idempotency rules define the shared lifecycle when background execution never occurs?
- Does Cloud Sync permit unattended decryption while a native device is locked, or require user presence and accept foreground-only encrypted sync?
- How are encryption keys enrolled on a second device and recovered after browser storage clearing, app reinstall, native key invalidation, or device replacement, without making the cloud provider the plaintext authority?
