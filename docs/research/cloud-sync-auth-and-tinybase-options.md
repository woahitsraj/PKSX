# Cloud Sync authentication and storage options that fit TinyBase

Research for [Research authentication and storage options that fit TinyBase](https://github.com/woahitsraj/PKSX/issues/410), a ticket on the map [Wayfinder: Cloud Sync for Saves](https://github.com/woahitsraj/PKSX/issues/302).

**Question.** Which authentication and storage solutions can serve as one Sync Provider that owns both identity and storage, and work well with TinyBase synchronization on web/PWA and Capacitor?

**Scope.** This file is evidence for a later provider-selection effort. The map stays provider-neutral. Nothing here selects a provider.

**Sources.** Official documentation and published packages, read on 2026-10-02: TinyBase 10.0.1 (type documentation and the agent skill that ship in the npm package, plus tinybase.org), Better Auth 1.7 documentation, Supabase, Firebase, Cloudflare, and Clerk documentation, Capacitor 8 documentation, Apple and Android developer documentation, RFC 8252, and the WHATWG WebSockets standard. PKSX locks TinyBase 8.5.0 and uses `@sveltejs/adapter-static`, so PKSX has no application server today. [PKSX package manifest](../../package.json), [TinyBase releases](https://tinybase.org/guides/releases/), [Better Auth documentation index](https://better-auth.com/docs/llms.txt)

Sentences marked **Inference** are conclusions from the cited sources. They are not statements made by a source.

## Answer

TinyBase does no authentication. Each TinyBase server component tells the host to authenticate the WebSocket upgrade request before TinyBase sees it. Thus any provider that can verify a credential in front of the upgrade request can protect TinyBase traffic. The real differences between candidates are where the TinyBase server can run, and how much identity code PKSX must operate. [TinyBase `createWsServer`](https://tinybase.org/api/synchronizer-ws-server/functions/creation/createwsserver/), [TinyBase `getWsServerDurableObjectFetch`](https://tinybase.org/api/synchronizer-ws-server-durable-object/functions/creation/getwsserverdurableobjectfetch/)

TinyBase names a Cloudflare Durable Object as "the recommended production WebSocket server". It is the only hosted shape with a first-class TinyBase synchronizer server. Supabase has a first-class TinyBase persister, but not a synchronizer server. Firebase and Clerk have no TinyBase integration. [TinyBase Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md), [TinyBase import paths](https://tinybase.org/skills/build-with-tinybase/references/import-paths.md)

All four candidate groups can meet the provider-neutral contract in a browser and an installed PWA. No candidate documents Capacitor as a supported target. In a Capacitor WebView each candidate needs the same pattern: sign-in in the system browser, a deep link back to the app, and a bearer credential held by the app. [Capacitor configuration](https://capacitorjs.com/docs/config), [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)

Better Auth is a library, not a hosted service. With Better Auth, PKSX operates the identity service and its database. This has a direct effect on the ticket #350 decision that PKSX never handles sign-in secrets. See [the Better Auth conflict](#provider-neutral-needs-that-a-strong-candidate-does-not-meet). [Better Auth comparison](https://www.better-auth.com/docs/comparison)

## TinyBase synchronizers, persisters, and authorization

### What exists now

A synchronizer moves `MergeableStore` changes between peers. A persister saves and loads a store. Every synchronizer needs a `MergeableStore`. [TinyBase lifecycle reference](https://tinybase.org/skills/build-with-tinybase/references/lifecycle.md)

### How each one authenticates a client

TinyBase has no token parameter, no header option, and no connect hook for identity. The documentation moves the task to the host in each case.

| Component                                       | Authorization model in the TinyBase documentation                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WsServer` (Node)                               | "The WsServer does not authenticate or authorize URL paths or channel Ids." "For untrusted clients, authenticate the upgrade request and either grant access to all descendant paths or use a separate authenticated WebSocket for each authorized path." [API](https://tinybase.org/api/synchronizer-ws-server/functions/creation/createwsserver/)                                                                                                                                                                                                                                       |
| `WsServerDurableObject`                         | "`getWsServerDurableObjectFetch` performs no authentication." "Write the worker's `fetch` handler directly: validate the request, then forward a request of your own to the Durable Object stub. Rewriting the path at that point is the supported way to scope a client to a verified user or tenant, rather than trusting a path the client chose." [Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md), [API](https://tinybase.org/api/synchronizer-ws-server-durable-object/functions/creation/getwsserverdurableobjectfetch/) |
| Client Ids                                      | Derived from the `Sec-WebSocket-Key` header. "They change across reconnections and are not identities. Do not authorize on them." [Lifecycle reference](https://tinybase.org/skills/build-with-tinybase/references/lifecycle.md)                                                                                                                                                                                                                                                                                                                                                          |
| `SupabasePersister`                             | Uses the Supabase client that the app passes in. "Row-level security applies to everything the Persister does, so it will read nothing and save nothing until a policy grants access to it." A per-user store needs a policy that compares `auth.uid()` to a column. [API](https://tinybase.org/api/persister-supabase/)                                                                                                                                                                                                                                                                  |
| `TinyBasePartyKitServer`                        | Subclass hooks `onRequest`, `canSetTable`, `canSetRow`, `canSetCell`, and their delete forms receive the request or connection. PartyKit itself authenticates in static `onBeforeConnect` with a token in the socket query string. [API](https://tinybase.org/api/persister-partykit-server/), [PartyKit authentication](https://docs.partykit.io/guides/authentication/)                                                                                                                                                                                                                 |
| Database persisters (`pg`, `postgres`, `mssql`) | The caller passes a configured connection or pool. The persister "stays out of the way of how you authenticate". These run on a trusted server, not in the client. [TinyBase releases](https://tinybase.org/guides/releases/)                                                                                                                                                                                                                                                                                                                                                             |

The browser `WebSocket` constructor takes a URL and optional subprotocols. It cannot set an `Authorization` header. The handshake does send cookies for the target host. Thus a browser client can carry a credential in three places only: a cookie, the URL (path or query), or the `Sec-WebSocket-Protocol` value. [MDN `WebSocket()` constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket), [WHATWG WebSockets standard](https://websockets.spec.whatwg.org/)

**Inference.** The safe shape for PKSX is: the client gets a short-lived credential, opens the socket with that credential in the query string or subprotocol, the edge handler verifies it, and the handler rewrites the path to the verified account identifier. The client never selects its own room. A credential in a URL can appear in logs, so it must be single-use or expire in minutes.

**Inference.** A WebSocket stays open after the credential that opened it expires. TinyBase has no revalidation hook. The host must close sockets when it revokes a session, or set a maximum socket age, to keep revocation bounded. Supabase documents the same property for its own Realtime service: "Client access policies are cached for the duration of the connection." [Supabase Realtime authorization](https://supabase.com/docs/guides/realtime/authorization)

### Hosting shapes that TinyBase supports first-class

1. **Cloudflare Worker and Durable Object.** TinyBase calls this the recommended production server. One Durable Object serves one path and can keep a server copy in Durable Object SQLite. `create-tinybase` can generate this stack. Shared sockets and channel Ids are not supported on this server, because each path is a separate object. [Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md), [TinyBase Cloudflare guide](https://tinybase.org/guides/integrations/cloudflare-durable-objects/)
2. **Node process with `ws`.** `createWsServer` with a persister for each path (SQLite, PostgreSQL, or file). This needs a long-running server. [API](https://tinybase.org/api/synchronizer-ws-server/functions/creation/createwsserver/)
3. **Supabase as a persister target.** No WebSocket server. Each client saves and loads the store through the Supabase REST API, and receives changes through Supabase Realtime. [API](https://tinybase.org/api/persister-supabase/)
4. **PartyKit.** Marked experimental and limited to a plain `Store`. Not usable for `MergeableStore` replication. [API](https://tinybase.org/api/persister-partykit-client/)

Two facts limit the fit to PKSX's revision model:

- The Supabase persister "stores a JSON serialization of the whole Store in a single row of a table" and supports only JSON mode. **Inference.** Each save from an Installation rewrites the full row. The server does not merge. An Installation that saves before it loads a newer row can overwrite that row. This is tolerable for small state, but it is a poor match for a growing set of immutable revision records. [API](https://tinybase.org/api/persister-supabase/)
- A SQLite-backed Durable Object has a 10 GB limit for each object and a 2 MB limit for each row, string, or BLOB. A received WebSocket message can be 32 MiB at most. Revision records fit. Save artifacts of several MB do not belong there, which agrees with ADR 0004. [Cloudflare Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [ADR 0004](../adr/0004-keep-save-artifacts-out-of-tinybase.md)

TinyBase also has a `middleware` module with a `WillApplyChangesCallback`. It runs before a `MergeableStore` applies incoming changes. **Inference.** A server store can use it to reject records that break PKSX rules, such as a change to an immutable revision. [TinyBase middleware](https://tinybase.org/api/middleware/)

## Capacitor WebView limits that apply to every candidate

The Capacitor WebView origin is `capacitor://localhost` on iOS and `https://localhost` on Android by default. The iOS scheme cannot be `http` or `https`. [Capacitor configuration](https://capacitorjs.com/docs/config)

- **Cookies.** A provider at `https://sync.example` is a different site from `localhost`. Capacitor states that "as of iOS 14, you cannot use 3rd party cookies by default", and offers `WKAppBoundDomains` as partial help. Better Auth documents the same Safari behavior: a third-party auth domain can cause "`Set-Cookie` being ignored" and "users appearing logged out after login". A cookie session is thus not reliable in the WebView. A bearer credential in app storage is. [Capacitor Cookies](https://capacitorjs.com/docs/apis/cookies), [Better Auth cookies](https://www.better-auth.com/docs/concepts/cookies)
- **OAuth redirects.** RFC 8252 says "native apps MUST NOT use embedded user-agents to perform authorization requests". Google's policy says a developer "must not direct a Google OAuth 2.0 authorization request to an embedded user-agent under the developer's control". Sign-in with an OAuth provider must leave the WebView. The Capacitor Browser plugin opens the system browser view (`SFSafariViewController` on iOS). [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [Google OAuth 2.0 policies](https://developers.google.com/identity/protocols/oauth2/policies), [Capacitor Browser](https://capacitorjs.com/docs/apis/browser)
- **Return to the app.** RFC 8252 lists a private-use URI scheme or a claimed `https` URL as the redirect target. Capacitor delivers both through `App.addListener('appUrlOpen')`. Universal Links and App Links need `apple-app-site-association` and `assetlinks.json` files on a domain that PKSX controls. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [Capacitor deep links](https://capacitorjs.com/docs/guides/deep-links)
- **Passkeys.** An Android WebView needs `androidx.webkit` 1.12.0 or later, `setWebAuthenticationSupport`, and Digital Asset Links to a website that the app owns. It does not support conditional mediation. **Inference.** A passkey ceremony is simpler in the system browser, on the provider's own origin, than in the WebView. [Android Credential Manager with WebView](https://developer.android.com/identity/sign-in/credential-manager-webview)
- **Apple rules.** An app that supports account creation "must also offer account deletion within the app". Deactivation alone is not sufficient. An app that offers a third-party login must also offer an equivalent privacy-preserving login service, unless it uses only its own account system. An app with Sign in with Apple must revoke the Apple tokens on deletion. [App Store Review Guidelines 5.1.1(v) and 4.8](https://developer.apple.com/app-store/review/guidelines/), [Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/)

**Inference.** The portable sign-in sequence for a Capacitor Installation is: open the provider sign-in page in the system browser, receive a single-use code through a deep link, exchange the code for a session with PKCE, and hold the credential in app storage. The earlier research file covers where that credential can be kept. [Web and Capacitor Cloud Sync constraints](https://github.com/woahitsraj/PKSX/blob/50154114bad9049a3dd7407f9623fb66ccc9a899/docs/research/web-capacitor-cloud-sync-constraints.md)

## Better Auth

Better Auth is a TypeScript library. It runs inside a server that the developer operates, and it keeps users in the developer's database. It has no per-user cost. It is at version 1.7.7. [Better Auth comparison](https://www.better-auth.com/docs/comparison), [Better Auth installation](https://www.better-auth.com/docs/installation)

### Session model

- **Cookie session, the default.** The `session_token` cookie is an opaque identifier for a row in the `session` table. The row holds `token`, `userId`, `expiresAt`, `ipAddress`, and `userAgent`. [Session management](https://www.better-auth.com/docs/concepts/session-management)
- **Expiry and renewal.** A session expires after 7 days by default (`expiresIn`). When the session is used and `updateAge` (default 1 day) is reached, the expiry moves forward. `disableSessionRefresh` stops this. A session is "fresh" for `freshAge` (default 1 day) after creation, and some endpoints need a fresh session. [Session management](https://www.better-auth.com/docs/concepts/session-management)
- **Cookie cache.** An optional signed `session_data` cookie lets the server skip the database for `maxAge` seconds. The cost is documented: "revoked sessions may remain active on other devices until the cookie cache expires". Without the cache, each check reads the session row, so revocation is immediate. [Session management](https://www.better-auth.com/docs/concepts/session-management)
- **Bearer plugin.** The server returns the session token in a `set-auth-token` response header. The client sends it as `Authorization: Bearer`. `auth.api.getSession({ headers })` accepts it. The documentation warns to use it only where cookies do not work. [Bearer plugin](https://www.better-auth.com/docs/plugins/bearer)
- **JWT plugin.** `/token` returns a JWT for the current session. A JWKS endpoint lets another service verify it with no database call. The default expiry is 15 minutes and is configurable. The subject is the user id by default. [JWT plugin](https://www.better-auth.com/docs/plugins/jwt)
- **One-time token plugin.** `generate` returns a single-use token tied to the current session. It expires in 3 minutes by default. `verify` returns the session. [One-time token plugin](https://www.better-auth.com/docs/plugins/one-time-token)
- **Stateless mode.** With no database, sessions live in a signed or encrypted cookie. The documentation states the cost: "you can't invalidate session easily". This mode does not fit the contract. [Session management](https://www.better-auth.com/docs/concepts/session-management)

### Sign out, recovery, deletion

- `signOut` ends the current session. `revokeSession({ token })` ends one named session. `revokeOtherSessions()` and `revokeSessions()` end the others or all. `listSessions()` lists active sessions. [Session management](https://www.better-auth.com/docs/concepts/session-management)
- Password reset uses a `sendResetPassword` callback that the developer writes, then `requestPasswordReset` and `resetPassword`. Other sessions are not revoked on reset unless `revokeSessionsOnPasswordReset` is `true`. Passwords are hashed with `scrypt` in the developer's database. Better Auth sends no email itself. [Email and password](https://www.better-auth.com/docs/authentication/email-password)
- `deleteUser` hard-deletes the user. It is disabled by default. It needs a password, a fresh session, or an email verification (`sendDeleteAccountVerification`) for OAuth users. `beforeDelete` and `afterDelete` callbacks run around the deletion. [Users and accounts](https://www.better-auth.com/docs/concepts/users-accounts)

**Inference.** `afterDelete` is the place to remove the account's Sync Profile, revision store, and artifacts, because the same Worker owns identity and storage.

### Sign-in methods

Email and password, more than 35 social providers, a generic OAuth plugin, magic link (5-minute link by default), email OTP (5 minutes by default), and passkeys through the `@better-auth/passkey` plugin, which uses SimpleWebAuthn. The passkey `rpID` and `origin` come from the auth server origin. Google, Apple, and Facebook also accept a provider ID token that the app obtained natively. [Better Auth documentation index](https://better-auth.com/docs/llms.txt), [Magic link](https://www.better-auth.com/docs/plugins/magic-link), [Email OTP](https://www.better-auth.com/docs/plugins/email-otp), [Passkey plugin](https://www.better-auth.com/docs/plugins/passkey), [Expo integration](https://www.better-auth.com/docs/integrations/expo)

### Runtime and database support

- Runtimes with documented handlers include Node frameworks, Hono, SvelteKit, and Cloudflare Workers. Workers need the `nodejs_compat` flag, because Better Auth uses `AsyncLocalStorage`. [Installation](https://www.better-auth.com/docs/installation), [Hono integration](https://www.better-auth.com/docs/integrations/hono)
- Built-in database support is SQLite, PostgreSQL, MySQL, and MSSQL through Kysely, plus Drizzle, Prisma, and MongoDB adapters. Cloudflare D1 works through the Kysely adapter. The CLI cannot reach D1, so migrations run from an endpoint in the Worker. [SQLite adapter](https://www.better-auth.com/docs/adapters/sqlite), [PostgreSQL adapter](https://www.better-auth.com/docs/adapters/postgresql), [Database concepts](https://www.better-auth.com/docs/concepts/database)
- The SvelteKit integration is a server hook (`svelteKitHandler` in `hooks.server.ts`). PKSX builds with `adapter-static`, so it cannot use that hook. **Inference.** PKSX would run Better Auth as a separate service and call it with the framework-neutral client. [SvelteKit integration](https://www.better-auth.com/docs/integrations/svelte-kit), [PKSX package manifest](../../package.json)
- When the API is on a different domain from the web app, Safari can block the cookies. The documented fixes are a first-party proxy path or a shared parent domain with `crossSubDomainCookies`. [Better Auth cookies](https://www.better-auth.com/docs/concepts/cookies)

### Native and Capacitor support

Better Auth documents Expo and Electron. It does not document Capacitor. The documentation index has no Capacitor page, and there is no `@better-auth/capacitor` package on npm. [Better Auth documentation index](https://better-auth.com/docs/llms.txt), [Expo integration](https://www.better-auth.com/docs/integrations/expo), [Electron integration](https://www.better-auth.com/docs/integrations/electron)

- The Expo plugin stores the session cookie in `expo-secure-store`, adds it to auth requests, and returns from social sign-in through a deep link. The app scheme must be in `trustedOrigins`. Requests to other endpoints must add the cookie by hand with `authClient.getCookie()`. This plugin depends on React Native modules, so a Capacitor app cannot use it as it is. [Expo integration](https://www.better-auth.com/docs/integrations/expo)
- The Electron integration uses the system browser, a custom protocol, and a PKCE code exchange. It also has a manual code-paste fallback for when deep links fail. This is the same pattern that a Capacitor app needs. [Electron integration](https://www.better-auth.com/docs/integrations/electron)
- A community package, `better-auth-capacitor` 0.4.0, does "social login via system browser with deep link callbacks" and caches the session in `@capacitor/preferences`. Better Auth states that community plugins "are not official or verified by the Better Auth team". [better-auth-capacitor](https://github.com/productdevbook/better-auth-capacitor), [Community plugins](https://www.better-auth.com/docs/plugins/community-plugins)

**Inference.** A Capacitor Installation can sign in with Better Auth through the bearer plugin, the system browser, and a deep link with a one-time token or PKCE exchange. PKSX must build and own this flow, or accept a community package. The origins `capacitor://localhost` and `https://localhost` must be in `trustedOrigins`, and the server needs CORS for them. [Options reference](https://www.better-auth.com/docs/reference/options), [Hono integration](https://www.better-auth.com/docs/integrations/hono)

### Better Auth with TinyBase

**Inference.** The Worker `fetch` handler calls `auth.api.getSession` or verifies a JWT from the JWT plugin, then forwards the upgrade to the Durable Object with the path set to the user id. On the web, with the API on the same site as the app, the session cookie travels with the WebSocket handshake. In Capacitor, the client puts a one-time token (3 minutes, single use) or a JWT (15 minutes) in the query string. The sources for each part are the bearer, JWT, and one-time token plugin pages and the TinyBase Durable Objects reference. [Bearer plugin](https://www.better-auth.com/docs/plugins/bearer), [JWT plugin](https://www.better-auth.com/docs/plugins/jwt), [One-time token plugin](https://www.better-auth.com/docs/plugins/one-time-token), [Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md)

## Alternatives that give identity and storage together

### Cloudflare Workers, Durable Objects, R2, and D1, with an auth library

Cloudflare has no end-user identity product for this use. An auth library such as Better Auth runs in the Worker and stores users in D1. The session facts are thus the Better Auth facts above.

- **TinyBase traffic.** First-class. The Worker validates the request and forwards it to `WsServerDurableObject`. The WebSocket Hibernation API lets the object sleep while clients stay connected, and duration charges do not accrue during hibernation. [Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md), [Cloudflare WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- **Artifact authorization.** Two documented ways. A Worker with an R2 binding checks the request in code and then calls `put`, `get`, or `delete`. The developer "must now define authorization logic". Or the Worker issues a presigned URL for `GET`, `HEAD`, `PUT`, or `DELETE` that is valid from 1 second to 7 days. Presigned URLs "work with the S3 API domain and cannot be used with custom domains", and Cloudflare says to "treat presigned URLs as bearer tokens". A Worker request body can be 100 MB on the Free and Pro plans, which is more than a save artifact. [R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-usage/), [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)
- **Cost shape.** Usage-based, with no per-user charge.

| Product                                       | Free                                                                        | Paid                                                                                                                                      |

### Supabase (Auth, Storage, Postgres)

- **Session model.** A session is an access token (a JWT) and a refresh token. The access token default expiry is 1 hour. A refresh token never expires but can be used once, with a 10-second reuse interval. Inactivity timeout, time-boxed sessions, and single session per user need the Pro plan. The model is bearer tokens, not cookies, and the client can use a custom `storage` adapter. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [Supabase PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow)
- **Sign out.** Scopes are `local` (this session), `others`, and `global` (all sessions). JavaScript defaults to `global`. "Access Tokens of revoked sessions remain valid until their expiry time." A server can check that the `session_id` claim still has a row in `auth.sessions`. [Supabase sign out](https://supabase.com/docs/guides/auth/signout), [Supabase sessions](https://supabase.com/docs/guides/auth/sessions)
- **Identifier.** The user `id` is a unique identifier, and it is the `sub` claim that policies read. [Supabase users](https://supabase.com/docs/guides/auth/users), [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)
- **Recovery.** `resetPasswordForEmail` then `updateUser`. The built-in email service is limited to 2 emails each hour, so production needs custom SMTP. [Supabase passwords](https://supabase.com/docs/guides/auth/passwords)
- **Deletion.** `auth.admin.deleteUser` "requires a `service_role` key" and "should only be called on a server". A user-started deletion thus needs a server function that PKSX writes. [Supabase `deleteUser`](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser)
- **Sign-in methods.** Email and password, OAuth, phone, SAML, and ID-token sign-in for native Google and Apple flows. Passkey sign-in is experimental: "The API may change without notice." [Supabase users](https://supabase.com/docs/guides/auth/users), [Supabase Google sign-in](https://supabase.com/docs/guides/auth/social-login/auth-google), [Supabase passkeys](https://supabase.com/docs/guides/auth/passkeys)
- **Capacitor.** The native deep-linking guide covers Expo, Flutter, Swift, and Kotlin. It does not name Capacitor. Supabase does publish Ionic tutorials. The PKCE flow stores the code verifier locally, the code is valid for 5 minutes, and the redirect URL (a custom scheme is allowed) must be on the allow list. **Inference.** The bearer model makes Supabase Auth a low-risk fit for the WebView, with the system browser and deep link for OAuth. [Supabase native deep linking](https://supabase.com/docs/guides/auth/native-mobile-deep-linking), [Supabase Ionic tutorial](https://supabase.com/docs/guides/getting-started/tutorials/with-ionic-vue), [Supabase PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow)
- **TinyBase traffic.** The `SupabasePersister` works under row-level security and Realtime. Realtime "checks a client's `SELECT` policy before it will send that client a change". The whole-store single-row limit above applies. Supabase has no TinyBase synchronizer server. [TinyBase Supabase persister](https://tinybase.org/api/persister-supabase/)
- **Artifact authorization.** Row-level security policies on `storage.objects`. "By default Storage does not allow any uploads to buckets without RLS policies." A policy can limit a user to a folder named by `auth.jwt()->>'sub'`. Uploads need `INSERT`, downloads need `SELECT`. [Supabase Storage access control](https://supabase.com/docs/guides/storage/security/access-control)
- **Cost shape.** Free: 50,000 monthly active users, 500 MB database, 1 GB file storage, 5 GB egress, 50 MB maximum upload, 200 Realtime connections, 2 active projects, and a project is "paused after 1 week of inactivity". Pro: from $25 each month, 100,000 monthly active users then $0.00325 each, 8 GB disk, 100 GB file storage then $0.0213 per GB, 250 GB egress then $0.09 per GB. [Supabase pricing](https://supabase.com/pricing)

### Firebase (Authentication, Cloud Storage)

- **Session model.** An ID token (a JWT) lasts one hour. A refresh token lasts until the user is deleted or disabled, or "a major account change is detected", such as a password or email update. The SDK renews the ID token. The model is bearer tokens. [Firebase manage sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)
- **Sign out and revocation.** The client signs out the local Installation only. `revokeRefreshTokens` in the Admin SDK ends all refresh tokens for a user, so "sign out everywhere" needs server code. ID tokens stay valid until their one-hour expiry unless the server calls `verifyIdToken` with `checkRevoked`, which costs a network request, or Security Rules compare `auth_time` to a stored revoke time. [Firebase manage sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)
- **Identifier.** The `uid` is "unique to the Firebase project" and is the `sub` claim. Another service can verify the ID token with a third-party JWT library and Google's public keys. [Firebase manage users](https://firebase.google.com/docs/auth/web/manage-users), [Firebase verify ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)
- **Recovery and deletion.** `sendPasswordResetEmail` uses Firebase's own email templates. The client can call `deleteUser`, and "the user must have signed in recently". [Firebase manage users](https://firebase.google.com/docs/auth/web/manage-users)
- **Capacitor.** Firebase documents Cordova, not Capacitor. `signInWithRedirect` fails in browsers that block third-party storage (Chrome 115 and later, Firefox 109 and later, Safari 16.1 and later) unless the app applies one of five fixes. The fix that suits a WebView is to "handle provider sign-in independently" and then call `signInWithCredential`. [Firebase Cordova](https://firebase.google.com/docs/auth/web/cordova), [Firebase redirect best practices](https://firebase.google.com/docs/auth/web/redirect-best-practices)
- **TinyBase traffic.** TinyBase has no Firebase persister or synchronizer. **Inference.** PKSX would host a TinyBase server elsewhere and verify Firebase ID tokens there, which splits storage across two vendors. [TinyBase import paths](https://tinybase.org/skills/build-with-tinybase/references/import-paths.md), [Firebase verify ID tokens](https://firebase.google.com/docs/auth/admin/verify-id-tokens)
- **Artifact authorization.** Cloud Storage Security Rules read `request.auth` and `request.auth.uid`, and can limit size with `request.resource.size`. [Firebase Storage security](https://firebase.google.com/docs/storage/security)
- **Cost shape.** Authentication is free up to 50,000 monthly active users. Cloud Storage for Firebase now needs the pay-as-you-go Blaze plan, with a no-cost tier of 5 GB stored. The free Spark plan sends 150 password reset emails each day. [Firebase pricing](https://firebase.google.com/pricing), [Firebase Storage plan changes](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024), [Firebase Authentication limits](https://firebase.google.com/docs/auth/limits)

### Clerk, with separate storage

- **Session model.** A hybrid. A long-lived client token is the source of truth. A session token is a JWT that "expires after 60 seconds", and the SDK renews it on a 50-second interval. Clerk can revoke a session through its database record. **Inference.** Revocation stops renewal, so it takes effect within about one minute. [How Clerk works](https://clerk.com/docs/guides/how-clerk-works/overview)
- **Verification.** Another service verifies the session token with Clerk's JWKS. The token is in the `__session` cookie for a same-origin request or the `Authorization` header for a cross-origin request. `sub` is the user ID and `sid` is the session ID. [Clerk manual JWT verification](https://clerk.com/docs/guides/sessions/manual-jwt-verification), [Clerk session tokens](https://clerk.com/docs/guides/sessions/session-tokens)
- **Sessions.** The default maximum lifetime is 7 days. A custom lifetime and inactivity timeout need a paid plan in production. `user.getSessions()` lists active sessions, and the Backend API `revokeSession` signs a session out. [Clerk session options](https://clerk.com/docs/guides/secure/session-options), [Clerk `User` object](https://clerk.com/docs/js-frontend/reference/objects/user.md), [Clerk `revokeSession`](https://clerk.com/docs/reference/backend/sessions/revoke-session)
- **Deletion.** `user.delete()` deletes the current user when `deleteSelfEnabled` is true. Clerk does not know about PKSX storage, so PKSX must also delete the Sync Profile data. [Clerk `User` object](https://clerk.com/docs/js-frontend/reference/objects/user.md)
- **Hosted sign-in.** Clerk has prebuilt components and a hosted Account Portal, so PKSX code would not handle a password. [Clerk Account Portal](https://clerk.com/docs/guides/customizing-clerk/account-portal)
- **Capacitor.** Clerk documents Expo, iOS, Android, Electron, and a Chrome extension. Its documentation index does not name Capacitor or Ionic, and SvelteKit support is a community adapter. [Clerk documentation index](https://clerk.com/docs/llms.txt), [Clerk Expo SDK](https://clerk.com/docs/reference/expo/overview)
- **Storage.** Clerk has none. Storage would be Cloudflare or another host, with Clerk tokens verified there. This is two providers, which does not match the ticket #350 decision that one Sync Provider owns identity and storage.
- **Cost shape.** Free up to 50,000 monthly retained users for each app. Pro is $25 each month, then $0.02 for each extra user. Passkeys, custom session duration, device tracking and revocation, and removal of Clerk branding are Pro features. [Clerk pricing](https://clerk.com/pricing)

### Provider-neutral needs that a strong candidate does not meet

1. **Better Auth and the "PKSX never handles sign-in secrets" decision.** Better Auth is a library in a server that PKSX runs. With email and password sign-in enabled, the PKSX-operated server receives the password and stores a `scrypt` hash in the PKSX-operated database. The PKSX client also posts the password from a form that PKSX builds, because Better Auth has no hosted page. To keep the ticket #350 decision, a Better Auth deployment must offer only delegated methods: social OAuth, passkeys, and magic link or email OTP. Or the map must state that the Sync Provider is a PKSX-operated service and that the rule applies to the PKSX app, not to that service. This is the main finding for the map. [Email and password](https://www.better-auth.com/docs/authentication/email-password), [Better Auth comparison](https://www.better-auth.com/docs/comparison)
2. **Capacitor sign-in is undocumented for all four.** No candidate names Capacitor as a supported target. The contract can still be met, because each one supports a bearer credential and a deep-link return. The contract should not assume cookies in the WebView.
3. **Supabase and Firebase revocation is bounded by token expiry.** The default bound is 1 hour unless PKSX adds a server-side session check. The contract should state the bound as a number that the provider adapter reports, not as "immediate".
4. **Supabase user-started deletion needs PKSX server code.** The client library cannot delete its own user.
5. **Firebase "sign out everywhere" needs PKSX server code.** The client can sign out only the local Installation.
6. **A live TinyBase WebSocket outlives its credential** on every candidate. The contract needs a rule for closing or re-checking open sockets after revocation.

## Ranked recommendation

This ranking is evidence for a later provider-selection effort. It is not a decision. The map stays provider-neutral.

1. **Cloudflare Workers, Durable Objects, R2, and D1, with Better Auth.** Best TinyBase fit: the only first-class, recommended synchronizer server. One operator owns identity, revision records, and artifacts, so account deletion can remove all data in one place. Lowest cost shape, with no per-user charge and free egress. Trade-offs: PKSX operates identity, must restrict sign-in to delegated methods to keep the ticket #350 decision, must build the Capacitor sign-in flow and artifact authorization, and must supply email delivery.
2. **Supabase.** Best managed fit: hosted identity, bearer tokens that suit the WebView, client-side sign out everywhere, and declarative storage policies. Trade-offs: the TinyBase integration is a whole-store persister with no server merge, so PKSX would need its own replication design or a separate TinyBase host. Deletion needs a server function. Revocation is bounded by token expiry. A free project pauses after one week without activity.
3. **Firebase.** Mature identity and declarative storage rules, with client-side deletion. Trade-offs: no TinyBase integration, Cloud Storage needs the Blaze plan, sign out everywhere needs Admin SDK code, and redirect sign-in needs a workaround.
4. **Clerk with separate storage.** Best hosted sign-in pages and the shortest revocation bound. Trade-offs: two providers, which does not match the one-provider decision. No Capacitor or first-party SvelteKit documentation. Several needed features are on the paid plan.

Main trade-off between ranks 1 and 2: rank 1 gives the best TinyBase and cost fit but makes PKSX the identity operator. Rank 2 gives managed identity but a weaker TinyBase fit. A mixed shape, Supabase Auth with a Cloudflare TinyBase server that verifies Supabase JWTs, is possible but breaks the one-provider decision in the same way as Clerk.

## Requirements this evidence fixes for the provider-neutral contract

1. **The credential for sync traffic is a bearer credential, not a cookie.** A cookie is an optional web optimization. [Capacitor Cookies](https://capacitorjs.com/docs/apis/cookies), [MDN `WebSocket()` constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket)
2. **The server selects the sync room from the verified account identifier.** The client never names its own room. [TinyBase Durable Objects reference](https://tinybase.org/skills/build-with-tinybase/references/durable-objects.md)
3. **The adapter reports a revocation bound.** Documented bounds range from immediate to 1 hour. Open sockets need a maximum age or a server-side close. [Session management](https://www.better-auth.com/docs/concepts/session-management), [Supabase sign out](https://supabase.com/docs/guides/auth/signout), [Firebase manage sessions](https://firebase.google.com/docs/auth/admin/manage-sessions)
4. **Sign-in leaves the WebView.** The contract needs "start sign-in" and "complete sign-in from a returned link" as two steps, so that a deep link can resume the flow after the app restarts. [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252), [Capacitor deep links](https://capacitorjs.com/docs/guides/deep-links)
5. **Account deletion is one provider operation that removes identity, revision records, and artifacts.** It must be available in the app. [App Store Review Guidelines 5.1.1(v)](https://developer.apple.com/app-store/review/guidelines/), [Apple account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/)
6. **Artifacts use a separate authorized channel from TinyBase records.** Every candidate has a blob path with its own authorization model and size limits. [ADR 0004](../adr/0004-keep-save-artifacts-out-of-tinybase.md), [Cloudflare Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
